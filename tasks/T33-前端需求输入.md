# T33 · 前端需求输入与简报理解

执行者：Codex（改前端、API、脚本、跑 mock）；复核：本会话 agent（deepseek-flash）
状态：待开始
日期：2026-11-03
依赖：T32（`--corpus`、`--thinking`、闲鱼分支）；Hanabi 6187；D16

## 目标

同事丢来的需求，能在 Hanabi 前端直接输入，模型读懂它再出稿——而不是现在只能填一个模型名。

现状两个缺口，本卡都要补：

1. 前端只有「模型名 / 数量 / 平台 / 背景」四个字段，没有地方放需求。
2. 简报是代码里写死的一句：`lib/content-ops-production.mjs` 第 45 行 `生成 ${count} 篇 ${model} 小红书图文。`

## 输入

- `hanabi/index.html`：生成表单（`content-ops-model` / `count` / `platform` / `backgroundMode`）。
- `hanabi/app.js`：表单提交与请求组装。
- `hanabi/lib/content-ops-production.mjs`：批次创建、`brief` 硬编码、请求去重、进度文案。
- `hanabi/server.mjs` 与 `lib/content-ops-*.mjs`：`/api/content-ops/generate` 入参校验。
- `scripts/gen-xhs-post.py`：`--model`、`--facts`、`--corpus`、`--thinking`。
- `rules/platform-rules.md`、`skills/xhs-post-generation/SKILL.md`、`docs/01-决策记录.md`（D18）。

## 设计要点

- **需求是自由文本，可选，≤1000 字**。为空时回退到今天的行为（简报自动拼“生成 N 篇 X 平台图文”），不改变老用法。
- **需求只定方向，不覆盖事实边界。** 需求里出现的能力、参数、性能、价格，没有 `facts.json` 支撑的，一律按 `suggestion` 处理，不得写成产品事实；需求里给的**服务条件**（好价、量大、快速稳定）视为用户提供，可写但不扩写（沿用 T24 的边界）。
- **需求参与去重**：同一个 `requestId` 改了需求 → 409，提示另起一批，避免半路换需求混批。
- **需求决定挑哪几组语料**：把需求原文 + 候选特征/角度清单一起交给模型，让它挑，并把挑中的 `feature` / `angle` id 回填到 manifest 与批次记录；不传需求时按账本正常轮换。
- **可回溯**：结果页显示本批需求原文和选中的特征，事后能对上是哪句话出的稿。
- **平台**：下拉先补「闲鱼」（依赖 T32 的闲鱼分支），需求与规则集按平台切换。

## 步骤

1. 前端加「需求」多行输入（textarea，1000 字上限，占位符给一条同事式例句），并把平台下拉补上闲鱼。
2. `app.js` 提交体加 `brief`；前端做长度与空值处理。
3. 服务端 `generate` 入参加 `brief`：长度校验、类型校验、纳入同一 `requestId` 的一致性判断（不一致返回 409）。
4. `content-ops-production.mjs`：删掉硬编码简报，改用入参 `brief`；为空时拼接回退串；把 `brief` 落库到批次记录，返回给前端展示。
5. 调用脚本时传 `--brief`（写入 scratch 临时文件或直接参数，按脚本约定，不把长文本塞进命令行）。
6. 脚本侧：`--brief` 进入请求体，作为「本次需求」段落；提示词明确「需求不得覆盖事实边界，缺 facts 支撑的一律写成建议」。
7. 语料挑选：把候选特征/角度列表与 brief 一起传给模型，要求返回选中的 id；无 brief 时走账本轮换。
8. 结果页展示需求原文与选中特征。
9. 用 mock / 隔离假模型验证以下（不产生真实收费调用）。
10. 更新 `docs/GUIDE.md`（前端怎么填需求、空着会怎样）、`README.md` 现状表、进度表；截图；归档；中文 commit 推送。

## 验收

1. 前端有需求输入框：空着能提交（回退老行为），填了能提交，超 1000 字提示并拒绝。
2. 批次记录与结果页能看到需求原文；manifest 里有选中的 `feature` / `angle` id。
3. mock 断言脚本请求体包含需求原文；**需求不得越过事实边界**：构造一句“支持 1M 上下文”但 facts 里没有，成稿中不得出现该断言（附对比）。
4. 同 `requestId` 改需求 → 409，提示另起一批。
5. 不填需求时：请求体与改前一致（贴对比），老用法不受影响。
6. 平台选闲鱼时能出稿（依赖 T32），需求与规则集按平台切换。
7. 截图：前端输入一句同事式需求 → 结果页显示需求与选中特征。
8. 不发布；不在未授权时发起真实收费调用。

## 规矩

- 只改必要文件，不重构 Hanabi（D16）。
- 需求不是事实，也不是规则：不能覆盖禁词、平台规则、事实边界。
- 需求为空时行为必须与今天一致；任何新字段都要能缺省。
- 不改 rules、不在代理层注入逻辑。

# RaDesign 内容创作流程档案（整合版）

本流程同时适用于 AI 内容创作炼丹炉的开炉创作。涉及联网调研时，先按 `research-playbook.md` 生成证据卡；涉及多账号时，共用研究底稿但分别重写；涉及图片、视频或音频时，再按 `multimodal-playbook.md` 分配媒介任务。

## 总流程

```text
接收多种素材 → 区分来源与可信度 → 找受众问题 → 确定一句话核心承诺
→ 建立内容母板 → 决定媒介与分工 → 筛选案例/提示词/视听证据
→ 分媒介制作 → 结构与节奏修改 → 证据与流程核验 → 人工感终检
→ 规格、版权与发布检查 → 人工确认 → 最终交付
```

## 传播优先的内容母板（2026-09-07 用户明确修订）

做品牌传播或热点内容时，把“传播”放在资料整理之前，而不是成稿之后才补标题。先写四个字段：

- **首屏冲突**：什么一句话能让目标读者停下来。
- **主命题**：读者看完最可能转述的判断是什么。
- **证据链**：哪三个案例、数据或过程能让这句判断站住。
- **行动落点**：读者下一步要试什么、选什么、咨询什么或转给谁。

然后按“注意力 → 信任 → 转述 → 行动”重排资料。可以先用强词、危机和反差争夺注意力，再在第二屏开始补对象、时点、来源和边界。不要为了显得严谨，把第一屏写成摘要或免责声明；也不要为了显得传播，把证据和归因全部删掉。

当内容同时承担品牌曝光、专业教育和产品转化时，允许主标题或主张比证据更大胆，但要做“承诺—兑现”检查：标题的夸张是否能在正文被具体案例解释，情绪词是否有真实对象，身份判断是否留有条件，CTA 是否在读者完成信任建立后出现。

## “事实骨架 + 高位散文”双层写法（2026-09-08 单样本炼入）

需要降低 AI 味时，不把整篇文章统一改成口语或抒情，而是先分层：

- **事实骨架**：产品、数据、步骤、案例、失败、价格、来源和风险；要求清楚、准确、可复核。
- **高位散文层**：开头的方向判断、段落之间的意义提升、作者立场、结尾余韵；要求有重量、有节奏、有具体意象。

编辑顺序为：先写清事实骨架，再找一条贯穿全文的方向轴（向上/向下、从表面到深处、从热闹到长期、从能力到责任等），最后只在关键节点加入高位散文段。每篇通常保留 2—4 个高位段落即可，避免抒情稀释信息密度。

高位段落的生成公式可以是：具体经验 → 身体/空间意象 → 价值判断 → 留白或回环。比如先写一次返工、一次等待或一次失败，再把它提升为对耐心、判断、审美或责任的看法；不要凭空从“大时代”开始喊。

终检时增加三问：

1. 这段抒情是否由前文事实托住？
2. 这段文字是否有明确方向，而不是漂亮形容词？
3. 如果删掉意象，作者的判断还剩什么？如果什么都不剩，说明只是装饰。

## 普通人意义型模型文章的“处境—交互—边界”证据卡（2026-09-08 单样本炼入）

遇到“发布不热但可能对普通人有意义”的模型文章，先记录：

- **处境**：谁在什么时间、什么现实压力下使用模型；不把“普通人”写成抽象人群。
- **原始问题**：用户具体问了什么，是否包含失业、债务、孤独、创作或身体状态等敏感内容。
- **模型回应**：保留原文/截图，标出事实回应、情绪回应、想象性比喻和可能有风险的断言。
- **即时变化**：用户报告的是被安慰、说清楚、停止自责、重新行动，还是只是觉得文字好看；不要替用户补写效果。
- **现实缺口**：工作、收入、医疗、法律、安全、人际支持等外部问题是否仍未解决。
- **边界与转介**：若涉及自伤、严重抑郁、医疗或危机信号，明确模型不能替代专业帮助，并提供现实支持方向；不要把文章写成诊断或治疗建议。

正文按“反热点 → 具体处境 → 一次交互 → 价值重估 → 边界 → 回到普通人”推进。将模型价值拆成三层：任务能力、信息帮助、情绪/表达支持。三层不互相替代；“让人好受一点”是一个可记录的体验结果，不等于疗效，也不等于模型理解了人的全部处境。

截图类素材要保留时间、提问、模型名称/版本和上下文；对失业、健康、债务等敏感信息做必要打码，并确认转载授权。图片承担“真实发生过的交互”证据，不用只截模型最漂亮的一段话。

## 资料阶段

把内容分为：官方说明、作者亲测、操作步骤、提示词、模型和参数、生成结果、文字、图片、视频、音频、价格活动、链接、版权/隐私信息。建立素材清单，记录格式、来源、授权、用途和每条结论的出处；只有官方说明不得写成“我测试后发现”。

## 选题与案例

作者亲测型模型文章增加“可比实测协议”：尽量固定 Prompt、输入素材、工具入口和任务目标；同时记录模型版本、思考/速度模式、额度或成本、耗时、成功结果、失败点和人工介入。新旧对比优先采用同一任务复跑，避免把不同难度案例拼成单向结论。成功案例之外至少保留一个失败、边界或待确认项。

高密度首批实测增加“任务卡”字段：任务名称、核心 Prompt、输入素材、使用模型、调用的外部软件/工具、开始与结束时间、是否可交互、失败或人工介入点、截图/录屏/链接证据。测试顺序可采用“经典小题 → 视觉/动效 → 3D/游戏 → 外部软件 → 项目原型”，先建立基线，再逐步扩大任务复杂度。若一天内连续运行大量案例，记录额度消耗和测试窗口只用于说明实验条件，不外推为普遍成本或稳定性。

高密度实测教程增加“奇观—复现—代价”三栏：

- **奇观**：标题和首屏使用的具体结果、数量、耗时或异常细节；记录它为什么一眼能被看懂。
- **复现**：输入素材、模型入口、外部软件、插件/MCP、关键 Prompt、人工选择、每轮修改和最终可交付结果。
- **代价**：Token/额度、运行时间、设备性能、版权/权限、未解决问题和适合的推理档位。

文章先用奇观建立注意力，再用跨场景案例证明不是单点巧合，再选择一个主案例做完整教程；最后必须有成本刹车。案例快览不应和教程重复全部步骤，教程也不能省略失败和人工判断。

对标题中的具体数字增加“口径核对”：确认数字来自作者记录、工具界面、估算还是二次转述；正文标明时间点和工具环境。没有独立复核时，使用“作者记录/本次任务生成了约……”而不是“模型能稳定生成……”。

跨媒介工作流增加“链路卡”：Brief、故事/分镜、Previs 场景、参考帧、生成镜头、剪辑时间线、调色结果分别记录输入、输出、工具、人工决策和证据。跨模型测试尽量固定 Brief，分别记录动作、构图、氛围、信息完整度、角色/场景一致性和后期可编辑性。出现 IP 或同人素材时，增加版权风险字段，不把技术可行性写成可商用结论。

社交平台截图类视觉样本增加“界面—结果对照卡”：原始平台/账号、标题与发布时间、生成过程状态、最终成品、评论/互动数据、裁切与排版方式、版权与隐私处理。把互动量标为反馈信号，把过程状态标为可复查证据，两者不得混为模型质量结论。

多账号案例墙增加“扩散地图”字段：账号、任务类型、作品/过程证据、评论质疑、互动信号、来源时间和版权/隐私处理。案例至少覆盖三种不同工作域；先按任务分组再排版，避免按账号顺序堆叠。编辑结论只写“话题扩散/用法多样/读者关注点”，不把多条社交帖子拼成统一实测结论。

当文章展示 AGENT.md、Skill、提示词或配置时，将其单独登记为“资产交付”，记录作者原始用途、适用前提、不可泛化部分和安全/权限影响；不得因为样本有效就把个人规则升级成通用最佳实践。强模型上线后的规则优化可采用“减法审查”：删掉过度限制前，先区分系统/安全约束、项目事实约束与可选偏好，并保留变更前后对照。

选题至少满足：有具体问题、有作者关系、有读者收益、有可展示证据。用一个主案例证明主观点，再用最多两个补充案例展示通用性或新能力。若资料只有功能清单、没有个人操作或结果，先建议补资料或只做分析，不直接写成体验稿。

模型发布或热点稿可把评论区/社群反馈当作“阻力采样”，只提炼反复出现的决策问题（例如价格、地区可用性、订阅覆盖、替代品期待和实际偏好），用来调整正文的限制段与 CTA；评论者的具体断言仍需独立核验，不把单条留言升级为事实。

涉及 API 安全策略时，素材清单增加四类字段：触发条件、受影响范围、兼容路径、迁移风险。先画出“旧调用 → 新规则 → 严格/兼容分支”的最小状态图，再写文章；这样能避免只讲厂商动机、不讲开发者下一步，也能把尚未确认的账户覆盖范围单独标为待核验。

重大模型发布日增加“证据分层”标记：A 类为作者账户/界面亲测，B 类为官方公告、图表、System Card 与模型文档，C 类为官方合作伙伴案例或估算，D 类为评论区和社区传言。正文可以用 A+B 建主线、用 C 补充场景、用 D 只做读者问题采样；不得用 C/D 的口吻伪装成编辑部实测。

面向大众的模型科普稿，增加“术语翻译表”：每个新术语记录技术定义、读者类比、类比失效边界和一条可核验来源。案例筛选优先覆盖不同工作域，而不是选择三个相似的炫技演示；若只能取得厂商案例，统一标为“官方展示/官方称”。

面向大众的官方发布科普增加“工作后果表”：每条参数、跑分或机制对应一个可感知问题（步骤数、跨工具连续性、失败修正、等待时间、任务总成本、人工复核）。先写一个核心问题，再筛掉不能服务该问题的指标。客户/合作伙伴案例登记来源层级与授权，不把客户自述外推成普遍效果；涉及 AGI、零日漏洞等高张力结论时，单独标记官方说法、第三方证据和未决争议。

产业链推演增加“工作负载—瓶颈—环节”表：记录模型变化带来的调用轮次、KV-Cache、CPU/沙盒、网络搬运、存储层级和功耗变化；每个受益环节注明证据等级（已披露/行业共识/作者推演）与可证伪指标。市场段另列股价、订单、资本开支、供需和替代方案，不能用单日涨跌证明长期产业趋势。

专业工程评测增加“交付分层表”：输入是否已确认、模型执行的局部操作、自动检查结果、人工复核项、实物/线上验证项、可交付结论。遇到压缩回放或宣传演示，记录演示时长与实际任务时长是否可知；未知时不得用演示时长代替设计周期。硬件任务至少分为工程文件、设计规则、制造、上电/带载四层；嵌入式任务至少分为代码、编译、下载运行、设备读数和异常处理五层。

现实世界多模型对比增加“同题对比协议”：

- **固定项**：同一设备/软件、同一入口和权限、同一输入素材、同一原始 Prompt、同一人工看护与急停条件、同一验收仪器和日志方式。
- **故意开放项**：允许模型自行选择动作顺序、速度、路径、工具调用和验证方式；若任务模糊度是测试变量，要明确写出未定义的词（如“转一遍”“做好”“检查一下”）。
- **安全底线**：统一设置不可越过的物理边界、最大速度/力量、人工确认、急停和回滚；模糊 Prompt 不能成为放松安全的理由。
- **记录项**：动作序列、参数、反馈值、等待/重试、异常分支、成功判定、最终报告、脚本/配置交付、工具调用、Token、耗时和账单。
- **复盘项**：第一次报告与后续审计是否一致；模型是否承认误报、补充验证或修改运行门禁。

对“完成”使用分层验收，而不是二元标签：

1. 动作发生；
2. 目标状态达到；
3. 反馈在阈值内稳定；
4. 异常能停止、重试或回滚；
5. 结果留下可复用交付物和证据链。

正文按“覆盖 → 风险 → 验证 → 交付 → 成本”横向排模型，避免先给总冠军再挑证据。可以用一张最小矩阵记录：模型、动作数、速度/边界、验证条件、异常处理、交付物、工具调用、耗时、Token/账单、人工介入和未决风险。成本比较必须注明是否同题、是否同上下文、是否包含缓存/回退/后续复盘，不能把不同会话的账单当成严格单次成本。

实体设备测试另加“安全现场卡”：启动前提醒、人的位置、线缆/负载状态、急停方式、倒计时/二次确认、设备磨损和不可逆后果。视频用于证明动作与观感，串口/传感器/日志用于证明状态，二者不能互相替代。

当一篇稿件出现“官方估算 + 第三方实测 + 综合榜单”三种证据时，建立对照表记录：测量对象、模型模式、推理档位、是否含回退、成本口径、发布日期和来源层级。先解释冲突，再下结论；不能挑对自己最有利的一组数字拼成单向叙事。

模型测评的素材表增加“基线强度”和“饱和度”字段：记录比较对象在该基准上的位置、分数是否集中、任务是否接近日常工作。发现新旧差距很大时，先检查旧模型是否为较弱版本或被 safeguard 影响，再决定能否写成能力跃升。

需要输出选型结论时，做一张最小决策矩阵：任务类型、首选模型、成本/速度代价、证据来源、尚未确认的风险。把作者立场和事实证据分栏，避免“我建议”掩盖证据不足。

涉及中国大陆读者时，增加“可获得性与替代选择”字段：服务是否开放、账户/地区限制、可用的本地或开源替代、价格与部署差异。该段只回答读者下一步怎么选，不把地缘情绪写成技术结论。

发布前传闻选题增加“传闻分层”字段：L1 为可复现的公开界面/路由现象，L2 为多个独立测试者的趋同观察，L3 为单个账号或内部代号，L4 为功能与竞争意图推演。正文以 L1/L2 建事实骨架，L3 作为线索，L4 只做情景分析；每段末尾写出证据边界和下一步核验点。

当文章同时覆盖能力、价格、科研和安全，先建立“模型/模式/入口/防护状态”矩阵，再录入每条分数和成本。曲线图解读应保留思考预算档位、任务基准、平均花费和是否计入被 safeguard 拦截的任务，避免跨图表做无效横比。

遇到跑分争议、页面回填或同一指标多次变化时，增加“证据漂移记录”：保存页面/预热稿/快照的时间、原始数字、后续数字、来源、评测配置和官方解释。先判断是版本、系统提示、工具链、样本或展示口径变化，再决定能否使用“提升/下降/作弊”等词。未经独立证据支持，不把指标修订升级为故意操纵。

若引用官方提示词指南来解释模型缺陷，建立“症状—官方建议—作者推断—适用边界”四列表；若同时推广榜单或追踪产品，另列“事实层、方法层、产品层、预测层”，避免用未核验预测替产品宣传造势。

## 提纲与骨架稿

提纲先写功能，不先雕句子：标题方向、开头钩子、核心观点、产品/功能简介、主案例、补充案例、限制、结尾行动。每个案例按“我想做什么→我做了什么→出现什么问题→我怎么改→结果如何”组织。长提示词前后要说明作用，图片和视频要标明承担的证据。

## 分层修改

1. 结构：开头是否太慢，产品是否出现太晚，主观点是否唯一，案例是否重复。
2. 证据：结论是否有结果、参数、截图、视频或前后对比；个人经验是否被写成普遍规律。
3. 流程：按钮、入口、模型、上传素材、节点和导出步骤能否复现；理论支持与实际成功要区分。
4. 语言：是否像设计师本人，是否出现官方腔、抽象套话、过度学术化或机械模板。
5. 视觉：重要操作是否有视觉锚点，素材与文字是否对应，是否需要失败/成功对比。
6. 校对与转化：核对产品名、模型名、参数、URL、价格和时间；自然交代适用人群、试用/优惠和下一步。

## “实测稿”与“时代评论稿”的双层编排（2026-09-07 单样本炼入）

同一批模型案例可以服务两种不同文章，但不能共用同一层级的组织方式：实测稿以交付边界为主，时代评论稿以能力稀缺性和读者处境为主。若要在一篇里兼顾传播和可信度，先做一张“案例—命题”表，给每个案例只分配一个论证功能：能力扩散、旧门槛、职业代价、失败边界或训练悖论。

写作时先确定一句可转述的中心判断，再把案例按情绪和认知递进重排；不要沿用资料收集顺序。推荐的检查顺序是：

1. 公共现场：读者为什么今天就该关心。
2. 视觉证据：哪个案例一眼能让人相信变化正在发生。
3. 代价映射：这个变化过去需要多少时间、技能或团队协作。
4. 能力拆分：哪些执行步骤可交给模型，哪些判断仍需人。
5. 悖论与边界：执行被压缩后，判断如何训练；演示离交付还差什么。
6. 下一步：读者能做的一个小实验，或组织/教育需要重新设计的一件事。

在编辑检查中增加四个传播字段：首屏冲突、主命题、可引用句、情绪落点。若一篇文章同时塞入能力盘点、失败记录、Token 教程和产品转化，必须指定一个主层、其余降为证据卡或附录；否则标题和首段会承诺多个不同阅读任务，削弱转发理由。

## 未来推演稿的“前提—机制—分叉”工作流（2026-09-07 单样本炼入）

写未来推演前，先建立一张推演表，而不是直接写结论：

| 层级 | 要回答的问题 | 写作要求 |
|---|---|---|
| 前提 | 哪个技术、制度或成本变化被假定成立？ | 明确是假设，不把愿景当事实 |
| 第一阶结果 | 企业/个人最先改变什么？ | 写具体流程、岗位、现金流或资源投入 |
| 中间机制 | 为什么这个变化会继续传导？ | 说明经营权、资产、责任和收益如何移动 |
| 第二阶结果 | 契约、组织和市场形态如何变化？ | 用条件句，避免单跳结论 |
| 分叉变量 | 哪些条件会把路径推向不同方向？ | 至少列两条路径及其关键瓶颈 |
| 验证信号 | 未来出现什么现象可支持或否证推演？ | 给出可观察的行业/组织指标 |
| 未决风险 | 谁可能受损，什么会阻断链条？ | 保留监管、责任、资产集中和分配冲突 |

主体按“企业经营 → 个人契约 → 生产资料 → 所有权 → 公司形态 → 社会分化”递进。每段只推进一层，并反复回答四个问题：谁投入、谁控制、谁承担失败、谁拿到剩余收益。若文章使用“新阶层”“公司消融”“全职不合算”等传播性命名，要在该段附近加一条条件限定，避免读者把标题判断当成事实陈述。

推演稿的证据可以分三档：A 为已发生的早期迹象或案例，B 为从前提推出的机制推论，C 为作者的价值判断和担忧。正文用 A 锚定现实、用 B 推进结构、用 C 制造问题意识；不要用 C 的情绪语气冒充 A 的事实。结尾不必给唯一答案，但要留下“下一步观察什么、谁需要提前调整”的行动问题。

## AI商业化分析的“用户—价值—预算”证据卡（2026-09-07 单样本炼入）

分析 C 端用户是否“值钱”时，不能只收集月活和增长。每个产品至少建立以下字段：

| 维度 | 要记录什么 | 常见误判 |
|---|---|---|
| 使用 | DAU/MAU、留存、使用频率、核心场景 | 活跃等于愿意付费 |
| 变现 | 订阅转化、ARPU、广告收入、API/席位/项目回款 | 收入数字不等于利润 |
| 成本 | 推理 Token、算力、客服、审核、渠道、补贴和硬件售后 | 免费用户没有成本 |
| 替代 | 用户迁移成本、免费竞品、模型可替换性、数据/工作流锁定 | 留存高等于护城河深 |
| 付费方 | 个人、企业部门、开发者、广告主、硬件购买者和平台 | 用户与买单者是同一人 |
| 期权 | 入口、品牌心智、未来新场景、生态分发、数据/反馈价值 | 当前不赚钱等于没有战略价值 |

文章结构优先采用“悖论 → 路径拆解 → 例外 → 战略转向 → 条件性结论”。订阅、广告、硬件不必都写，但若写了，每条路径都要回答：谁付钱、为什么现在付、替代品是什么、成本和合规压力在哪里、收入能否覆盖服务成本。

证据分层要单独标记：公司公告/财报/产品数据为一手事实；媒体报道和采访为二手证据；匿名闭门会与行业传闻只能作为线索；“我身边没有人付费”只能保留为作者观察，不能替代转化率。涉及行业总量、付费用户、广告收入、出货量和政策时点，必须记录日期、口径、样本范围与是否为估算。

结尾做“短期财务价值—长期战略期权”双轴判断：C 端可能当前是成本项，但仍值得保留入口；B 端可能更容易回款，但也伴随交付、采购、集成和责任成本。不要用“放弃 C 端”一刀切，改写成投入强度、维护基线、探索新场景和预算归属的组合决策。

## 专业工具深测的“瓶颈—压力样本—生产链路”工作流（2026-09-07 单样本炼入）

写专业工具评测前，先填一张生产可用性表：

| 层级 | 要问的问题 | 证据 |
|---|---|---|
| 行业瓶颈 | 这个赛道真正卡在哪里？ | 旧流程、常见失败、竞品现状 |
| 核心能力 | 产品解决的是几何、材质、拓扑、速度还是协作？ | 官方说明、技术路线、实测 |
| 压力样本 | 哪些输入能区分能力，而不是只展示漂亮结果？ | 混合材质、复杂结构、透明/细纹理、不同视角 |
| 管线过程 | 是否有预览、筛选、精修和可回退节点？ | 时间线、阶段产物、重跑成本 |
| 下游交付 | 文件能否编辑、导出、批量处理和进入现有工具？ | 工程文件、格式、插件/API/MCP、兼容测试 |
| 人工代价 | 还需要多少修改、重拓扑、贴图、绑定和检查？ | 前后对比、修改时长、失败清单 |
| 商业与战略 | 这个能力如何连接数据、客户和平台生态？ | 公司披露、客户场景、作者推断分层 |

3D/视觉工具至少把结果拆成：外观相似度、几何/拓扑、材质参数、贴图通道、动态/部件关系、格式兼容、批量与集成。不要把“出图快”当成“资产交付快”，也不要把 PBR、Mesh 或高斯等术语本身当成质量证明。

测试素材采用“单样本单问题”原则：铜/金属类测试反射与氧化层，陶瓷测试半透明与釉面，织物测试粗糙度和微表面，透明/自发光测试光学边界，多部件机械测试结构关系，角色/场景测试品类覆盖与编辑难度。每个样本记录输入、生成时间、阶段产物、具体缺陷、二次修改和是否能直接进入下游。

专业结论使用“能否进入生产”五级描述：

1. 只适合概念草图；
2. 可做预览和筛选；
3. 可编辑但需要明显人工修整；
4. 常见品类可直接进入部分渲染/展示流程；
5. 可批量、可集成、可追踪地进入生产管线。

对官方价格、速度、覆盖品类、路线图、SDK 和资本市场信息分开建账；价格与性能注明官方口径、版本和换算方式。公司数据壁垒、技术路线和未来世界模型等内容分成“已披露事实—合理推断—战略想象”，避免把发布稿写成投资背书。

## 必须人工确认

产品功能、版本、模型、价格、活动期限、链接、版权、隐私、作者亲身经历、生成结果、失败原因和最终语气。AI 不得自行补写“我用了整整一年”“成功率很高”“节省了多少”等未提供事实。

## 成稿自检

```text
有真实问题 + 有真实操作 + 有真实判断
```

如果读者读完只能得到“这是一个功能很多的平台”，而不能说出作者做了什么、哪里有用、哪里仍有限制，则文章还没有达到 RaDesign 标准。

## 多账号生产原则（2026-09-02 调研炼入）

三个账号不再原文同步，采用“一个研究底稿、三个受众版本”：未来API负责开发者与 API 转化，深度脑图负责企业信任与镜像/解决方案，多元探索负责 AI 创作、闪创与社区增长。允许同题，不允许同标题、同案例组织和同 CTA。

不与高频媒体只比发布速度。公司的壁垒应是实测证据、真实场景、可复现结果和业务承接。阅读量只做同账号、同栏目纵向参考；复盘同时看内容表现与 CTA 转化，不能从竞品阅读差直接推导标题因果。

## 交付声明与独立验收（2026-11-09 单样本强化）

来源：用户提供的 Rhea《Kimi K3.1 Pro 深度实测：理科满分，文科稍逊一筹》粘贴文本。只记录文本可观察的测试设计与证据边界，不确认测试真实性、不作账号风格终审；具体案例、数字和输入指纹统一保存在 content-ops 的 `data/model-corpus.md` 对应深度实测记录，避免第二份模型事实源。

适用于 Agent、代码、3D、图表和研究任务的深测：把厂商主张转成实际任务，先写验收条件与参考答案，再执行并保留版本；更改评分口径时注明原因，对受影响结果统一重评，不能事后只为某个交付放宽标准。写清入口、模式、输入、允许的工具和修改范围、轮次、人工介入及未测项；轮次、题数、交付物数和错误声明数分别统计，不能混用分母。

每项保留“原要求—模型完成声明—独立检查—真实结果—未验部分”。独立指检查依据可回溯、可重跑，不能只换个模型复述交付报告。分别检查数据与公式、几何尺寸与接口装配、多视角外观与颜色、实物或下游使用；自动检查覆盖一层不能替其他层出通过意见。尺寸数字版与读图版可用于发现约束表达问题，但同时改变输入信息、图纸版本或工具路径时，不能归因为某种提示词必然更好。

把不可达判断也列为有效输出：记录限制、论证或反例及复核；只有用户授权扩大修改范围后才继续，并在改后重新验证。不把诚实拒绝算作无能力，也不把口头“做不到”当作已经证明不可达。

验收器本身也要查：对异常回到原始文件，检查跨期映射、空行、单位与报告版本，记录误判及修正；保留原评分与更正原因。先按统一口径纠正验收器，再解释模型结果，不能把脚本输出当作终审权威。涉及研究时分别检查数字、引文、计算、假设与结论；允许检索的反编造题与闭卷题分别报告，不用前者推导整体幻觉率。

文章可按“实际使用问题—测试协议—结果先报—声明与缺陷逐项对照—条件化用法—待验证解释”组织，这是本篇结构观察，不是全局风格规定。结尾关于训练奖励、复核成本或独立验收行业的解释标为作者假说；单篇结果不能证明训练因果、所有榜单的覆盖范围或整个行业趋势。正向单例同样不外推为普遍可放心交付。

2026-11-09，InfoQ 工程测试样本补充（案例事实与指纹只保存在 content-ops GLM“十三、InfoQ”）：

- 执行前写清可编辑区、只读文件和输出白名单；“只改工作目录”与“根目录写报告”等例外要逐项明确。保护评分器、题目和启动协议的完整性，禁止删测试、硬编码样例和伪造日志；保护措施需验收，不能只凭模型自述宣称遵守。
- 可见评分器可以在各步执行后提供修复反馈，但迭代后的满分不是独立保留验收；另外冻结保留测试，记录评分器和题集版本、修复轮次及人工介入。这里的保留验收是后续方法建议，不倒写成来源文章已经实施。
- 分开保存评分器结果、模型点评及真实交付检查；另一模型打分不自动成为权威认证。检查小型明确定义任务的适用范围，列出未测的大仓库、多语言、并发、数据库和模糊规格等维度。
- 耗时分别记录墙钟、模型、工具和测试的起止范围；来源出现相互冲突的时间又缺日志时并列保留，不能自行减出“纯推理”时长。相对提升、百分点、输出 tokens 与货币成本也分别表述，条件不足时不互换。
